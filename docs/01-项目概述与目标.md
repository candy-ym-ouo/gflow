# 01 · 项目概述与目标

## 1. 项目背景

在绝大多数业务系统中，都存在大量"流程性"需求：请假审批、订单风控、发布上线、工单流转、退款审核……传统做法是在业务代码里为每条流程手写一套状态判断、步骤编排与异常处理，导致：

- **重复开发**：相似的审批/流转逻辑在不同业务模块中反复实现；
- **难以变更**：流程调整（增删节点、改审批人、改条件）必须改代码、发版本；
- **状态不可见**：流程走到哪一步、卡在谁手里、失败原因，缺乏统一视图；
- **恢复困难**：节点执行失败后缺少重试、补偿与人工干预机制，故障容易"卡死"流程；
- **难以测试**：流程分支多，缺少统一的校验与测试手段。

GFlow 的目标是提供一个**可配置、可持久化、可恢复、可观测**的通用工作流引擎，把"流程编排"从业务代码中剥离出来，让业务方用一份 JSON 定义即可描述完整流程，由引擎负责执行、推进、持久化与恢复。

## 2. 项目目标

1. **配置驱动**：用结构化定义描述工作流（节点、条件边、审批、自动动作、恢复策略），运行时解释执行；
2. **节点能力完备**：支持开始/结束、人工审批、自动动作、条件分支、并行汇聚、等待等节点类型；
3. **条件引擎**：支持比较、逻辑、存在性、正则、JSONPath 与内置函数，条件可组合、可求值失败降级；
4. **审批中心**：多种审批模式与审批操作（同意/驳回/转办/加签/委派），驳回可路由到指定节点；
5. **失败恢复**：节点级重试（固定/指数退避）、超时策略、死信隔离、补偿动作、手动干预与断点续跑；
6. **实例持久化**：实例、节点实例、审批任务、执行事件全量落库，重启后从断点继续；
7. **Schema 迁移**：版本化、嵌入式、幂等迁移，启动时自动执行；
8. **REST API**：定义管理、实例管理、审批操作、日志查询、健康检查与 SSE 事件流；
9. **后台执行器**：调度器 + Worker 池异步推进，租约机制保证多副本安全，幂等执行；
10. **运行校验**：定义校验、启动自检、健康检查与指标，配置错误在启动/提交时即被发现；
11. **简单前端**：静态页面提供仪表盘、定义编辑、实例监控、审批中心与日志视图；
12. **工程约束**：Go 源码（不含测试）行数 **>2000 且 <2200**，Go 源码文件数 **>20 且 <25**，严格分层、禁止单文件实现。

## 3. 非目标（Scope Out）

| 非目标 | 说明 |
| --- | --- |
| 图形化流程设计器 | 前端提供 JSON 编辑与校验，不实现拖拽式画布（可作为后续增强） |
| 分布式事务编排 | 引擎聚焦流程编排与恢复，业务数据的强一致性由业务侧事务保证 |
| 定时任务框架 | 仅支持"延迟等待"节点与调度器轮询，不做 cron 级任务系统 |
| 多租户隔离 | 定义与实例按工作区/命名空间区分，不实现租户级权限体系 |
| 代码生成 | 定义不生成业务代码，全部运行时解释 |

## 4. 术语表

| 术语 | 英文 | 说明 |
| --- | --- | --- |
| 工作流定义 | WorkflowDefinition | 描述流程的配置（图：节点 + 边 + 恢复策略），版本化管理 |
| 节点 | Node | 流程中的最小执行单元，有类型（start/end/approval/action/condition/parallel/join/wait） |
| 边 / 条件边 | Edge | 节点间的有向连接，可携带条件表达式；条件成立才走该边 |
| 条件表达式 | ConditionExpr | 基于实例上下文的布尔表达式，如 `days > 3`、`amount >= 10000 and risk == "high"` |
| 审批任务 | ApprovalTask | 实例中"人工审批"节点产生的待办，含审批人、模式、截止时间 |
| 自动动作 | Action | 由引擎自动执行的节点副作用，如 HTTP 回调、通知、等待、内置函数 |
| 实例 | WorkflowInstance | 一次具体流程运行，绑定定义版本与业务键（bizKey），有独立状态机 |
| 节点实例 | NodeInstance | 实例中某节点的运行态（状态、重试次数、输入输出快照） |
| 上下文 | Context | 实例级的键值存储，节点输入取自上下文，输出写回上下文 |
| 幂等键 | IdempotencyKey | 自动动作/节点的去重键，保证失败重试不产生重复副作用 |
| 死信 | Dead Letter | 超过最大重试次数后进入的终态（DEAD），可人工干预后重新入队 |
| 补偿 | Compensation | 节点失败/流程终止时对已完成副作用执行的逆向操作 |
| 执行器 | Executor | 后台组件：调度器扫描可推进实例，Worker 池执行节点 |
| 租约 | Lease | 执行器对实例的独占续租，防止多副本重复执行 |
| 迁移 | Migration | 数据库 Schema 的版本化演进 |
| 运行校验 | Validation | 定义提交时与实例推进时的正确性检查 |

## 5. 设计原则

1. **配置与执行分离**：定义（数据）与引擎（行为）解耦，定义可存可改可校验，引擎只依赖定义协议；
2. **分层单向依赖**：`model` 零依赖 → `store`/`condition`/`action`/`approval` 依赖 model → `engine` 编排以上模块 → `api`/`executor`/`validator` 在最外层组合；
3. **一切关键状态可持久化**：实例、节点、审批、事件全部落库，进程崩溃不丢进度；
4. **幂等优先**：节点执行、动作副作用、调度推进都必须可重放，以幂等键去重；
5. **失败可见可恢复**：任何失败都进入明确状态（重试中/死信/失败），并提供重试与人工干预入口；
6. **可观测**：执行事件全量记录，SSE 实时推送，健康检查与指标暴露运行状态；
7. **配置即契约**：定义在提交前经过完整校验，非法配置不允许入库与执行。

## 6. 用户故事（User Stories）

| 编号 | 角色 | 故事 |
| --- | --- | --- |
| US-1 | 业务配置员 | 我希望用 JSON 定义请假流程（提交→主管审批→HR 归档），提交时引擎校验配置合法性，避免带病上线 |
| US-2 | 业务配置员 | 我希望在条件节点中写 `days > 3 and (level == "senior" or amount >= 10000)` 这类表达式，无需改代码即可调整分支 |
| US-3 | 审批人 | 我希望在我的待办中心看到需要我审批的任务，可同意、驳回、转办、加签或委派，并留下意见 |
| US-4 | 运营 | 我希望看到每个实例当前停在哪个节点、经历了哪些事件，失败的原因与重试次数一目了然 |
| US-5 | 运维 | 我希望节点失败后引擎按策略自动重试（指数退避），超过次数进入死信，我能手动重新执行 |
| US-6 | 开发 | 我希望引擎提供 HTTP 动作与幂等保证，让外部系统回调（发通知、调风控）可安全重放 |
| US-7 | 运维 | 我希望服务重启后，未完成的实例能自动从断点继续推进 |
| US-8 | 管理员 | 我希望看到引擎健康状态与指标（待推进数、死信数、执行时长），并随时暂停/恢复/取消实例 |

## 7. 成功标准

- 一条典型审批流程（含条件分支、会签、超时重试）从定义提交到实例完成，全流程无需写任何业务代码；
- 节点失败可按策略自动恢复，进程重启不丢状态；
- 定义校验能在提交时拦截 >90% 的常见配置错误（非法类型、悬空边、表达式语法错误等）；
- Go 源码（不含测试）行数落在 (2000, 2200)，文件数落在 (20, 25)，且严格分层无循环依赖；
- 前端可完成：查看定义、启动实例、处理审批、观察事件流。
