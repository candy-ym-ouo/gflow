## 2. 工作流定义模型

### 2.1 图模型

工作流定义是一张**有向图**：`节点（Node）` 是执行单元，`边（Edge）` 是节点间的流转关系。边可携带**条件表达式**，条件成立才允许沿该边流转。

- 每个定义**有且仅有一个开始节点（start）**，实例从它启动；
- 每个定义**有且仅有一个结束节点（end）**，到达即实例完成；
- 普通节点（approval/action/wait）**出边为 0 或 1 条**（0 条时视为默认汇聚到结束，由校验器约束）；
- 条件节点（condition）出边 **≥ 2 条**，每条边带条件，按顺序求值、取**第一条成立**的边；全部不成立时走 `default` 边（必须配置）；
- 并行节点（parallel）出边 **≥ 2 条**，全部入边实例同时激活；
- 汇聚节点（join）等待**所有入边对应的并行分支完成**后才继续（屏障语义）。

### 2.2 节点类型

| 类型 | 关键字 | 行为 |
| --- | --- | --- |
| 开始 | `start` | 实例启动入口，仅一条出边，无副作用 |
| 结束 | `end` | 实例完成标记，入边汇聚后置实例为 COMPLETED |
| 人工审批 | `approval` | 生成审批任务，等待指定审批人处理；支持模式、驳回、转办、超时 |
| 自动动作 | `action` | 引擎自动执行动作（HTTP/通知/等待/函数），失败可重试 |
| 条件分支 | `condition` | 按条件表达式路由到唯一出边 |
| 并行 | `parallel` | 扇出：同时激活所有出边分支 |
| 汇聚 | `join` | 屏障：等待所有入边分支完成 |
| 等待 | `wait` | 延迟指定时长（或等待指定时间点）后自动继续，用于超时/定时场景 |

### 2.3 节点公共属性

| 属性 | 必填 | 说明 |
| --- | --- | --- |
| `id` | 是 | 定义内唯一 |
| `name` | 是 | 展示名称 |
| `type` | 是 | 上述 8 种之一 |
| `input` | 否 | 输入映射：从实例上下文取值，如 `{"days": "$.form.days"}` |
| `output` | 否 | 输出映射：执行结果写回上下文，如 `{"risk": "$.result.risk"}` |
| `timeout` | 否 | 节点超时（如 `30s`、`2h`），超时触发节点级超时策略 |
| `retry` | 否 | 重试策略（次数、间隔、退避），见第 6 节 |
| `onFailure` | 否 | 失败策略：`retry` / `fail` / `skip` / `compensate` / `toApproval` |
| `description` | 否 | 说明文字，展示给审批人/运营 |

### 2.4 边属性

| 属性 | 必填 | 说明 |
| --- | --- | --- |
| `from` / `to` | 是 | 起点/终点节点 id |
| `condition` | 否 | 条件表达式（字符串），为空表示恒真 |
| `order` | 否 | 同一起点的边按 order 升序求值（条件节点必填） |
| `default` | 否 | 是否为兜底边（条件节点必配且唯一） |

### 2.5 配置示例（请假审批流程）

```json
{
  "name": "leave-approval",
  "version": 1,
  "nodes": [
    {"id": "start", "name": "开始", "type": "start"},
    {"id": "mgr_approve", "name": "主管审批", "type": "approval",
     "config": {"mode": "single", "assignee": "$.form.manager",
                "timeout": "48h", "timeoutPolicy": "autoApprove"},
     "input": {"form": "$.form"}},
    {"id": "check_days", "name": "时长判断", "type": "condition"},
    {"id": "hr_approve", "name": "HR会签", "type": "approval",
     "config": {"mode": "countersign", "assignees": ["$role:hr"],
                "passRatio": 1.0}},
    {"id": "notify", "name": "通知结果", "type": "action",
     "config": {"kind": "http", "url": "http://notify-svc/api/v1/send",
                "method": "POST", "timeout": "10s",
                "idempotencyKey": "leave-${$.instance.id}-notify"},
     "input": {"to": "$.form.applicant", "status": "$.result"}},
    {"id": "end", "name": "结束", "type": "end"}
  ],
  "edges": [
    {"from": "start", "to": "mgr_approve"},
    {"from": "mgr_approve", "to": "check_days", "condition": "approved == true"},
    {"from": "mgr_approve", "to": "end", "condition": "approved == false", "default": true},
    {"from": "check_days", "to": "hr_approve", "condition": "days > 3", "order": 1},
    {"from": "check_days", "to": "notify", "condition": "days <= 3", "order": 2},
    {"from": "hr_approve", "to": "notify", "condition": "approved == true"},
    {"from": "hr_approve", "to": "end", "condition": "approved == false", "default": true},
    {"from": "notify", "to": "end"}
  ],
  "recovery": {"instanceMaxRetry": 5, "deadLetter": true}
}
```

## 3. 条件引擎

### 3.1 表达式语法

条件表达式为布尔表达式，支持：

| 类别 | 语法 | 示例 |
| --- | --- | --- |
| 比较 | `== != > >= < <=` | `days > 3`、`status == "closed"` |
| 逻辑 | `and or not` 与括号 | `days > 3 and (level == "senior" or amount >= 10000)` |
| 存在性 | `exists($.x)`、`empty($.x)` | `exists($.form.manager)` |
| 正则 | `matches($.email, "^[^@]+@[^@]+$")` | 邮箱/编号格式校验 |
| JSONPath | `$.a.b[0].c` 取值 | `$.risk.level == "high"` |
| 内置函数 | `len() contains() sum() startsWith() now() addDays()` | `len($.items) > 0`、`contains($.tags, "urgent")` |
| 字面量 | 字符串（双引号）、数字、布尔、null | `approved == true` |

### 3.2 求值上下文

条件（以及节点 input/output 映射）统一从**实例上下文（Context）**取值。上下文由以下部分合并而成（优先级从低到高）：

1. 定义级默认值（`definition.contextDefaults`）；
2. 启动实例时传入的 `context`（业务参数，如表单数据）；
3. 各节点 `output` 写回的值（动作结果、审批结果 `approved`/`opinion` 等）；
4. 系统内置键：`$.instance.id`、`$.instance.bizKey`、`$.instance.status`、`$.node.id`、`$.node.type`、`$.time.now`。

**求值规则**：
- 求值结果为真 → 该边/分支成立；为假 → 不成立；
- 引用的键不存在 → 视为 `null`（`exists`/`empty` 可显式判断），不会 panic；
- **求值失败（语法错误/函数异常）** → 按定义级 `onConditionError` 处理：`fail`（默认，实例失败）、`false`（视为条件不成立）、`skip`（跳过该边/分支）；
- 条件节点必须保证"至少一条边成立"（含 default 兜底），否则实例失败并记录原因。

### 3.3 条件节点路由算法

```
输入：condition 节点的出边列表（按 order 升序）
对每条非 default 边：求值 condition
  → 成立：返回该边，结束
全部不成立：返回 default 边（必须存在，校验器保证）
```

## 4. 审批业务逻辑（审批中心）

### 4.1 参与者解析

审批人由节点配置 `config.assignee / assignees` 声明，支持四种来源：

| 来源 | 写法 | 说明 |
| --- | --- | --- |
| 指定用户 | `"alice"` | 固定用户 |
| 上下文动态 | `"$.form.manager"` | 从上下文取用户 id |
| 角色 | `"$role:hr"` | 解析为角色下全部用户（按角色成员提供者） |
| 表达式 | `"$expr:managerOf($.form.dept)"` | 内置函数动态解析 |

解析失败（用户不存在/角色为空）时：按 `onAssigneeMissing` 策略处理：`fail`（默认）或 `toAdmin`（转给系统管理员）。

### 4.2 审批模式

| 模式 | 关键字 | 规则 |
| --- | --- | --- |
| 单人审批 | `single` | 指定 1 名审批人，通过即节点完成 |
| 会签 | `countersign` | 全部（或 `passRatio` 比例）审批人通过才通过；任一驳回即驳回 |
| 或签 | `any` | 任一审批人通过即通过 |
| 顺序审批 | `sequence` | 按 `assignees` 顺序逐人审批，前一人通过后激活下一人 |

审批结果写入上下文：`approved`（bool）、`opinion`（意见）、`approver`、`approvedAt`。

### 4.3 审批操作

| 操作 | API | 语义 |
| --- | --- | --- |
| 同意 | `approve` | 提交意见并同意；满足模式条件（会签比例/顺序）后节点完成 |
| 驳回 | `reject` | 驳回，按驳回路由（见 4.4）回到指定节点 |
| 转办 | `transfer` | 把当前任务转给另一审批人（原审批人退出） |
| 加签 | `addApprover` | 追加一名审批人参与当前任务（会签语义） |
| 委派 | `delegate` | 委托他人代审，原审批人仍可撤销 |
| 撤销 | `revoke` | 委派/加签场景的撤回操作 |

所有操作均校验：操作人必须是当前任务参与者（或管理员），且实例处于可操作状态（WAITING_APPROVAL 且未过期）。每次操作写入审批记录（操作人、动作、意见、时间），并触发实例事件。

### 4.4 驳回路由

驳回不是简单失败，而是**回到流程中的某个节点**重新走：

| 策略 | 说明 |
| --- | --- |
| `previous`（默认） | 回到上一审批节点（或上一节点），该节点重新激活 |
| `start` | 回到开始节点重新执行（常用于表单需修改的场景） |
| `node:<id>` | 回到指定节点 |
| `terminate` | 直接终止实例（状态 TERMINATED） |

驳回时携带驳回意见写入上下文（`$.reject.reason`），被驳回节点可将其作为输入展示给申请人。

### 4.5 审批超时与自动处理

审批任务支持 `timeout`（绝对/相对时间），超时后触发 `timeoutPolicy`：

| 策略 | 说明 |
| --- | --- |
| `remind` | 仅发送提醒（每 N 分钟一次，可配 `remindInterval`），任务保持等待 |
| `autoApprove` | 自动视为同意继续 |
| `autoReject` | 自动视为驳回（走驳回路由） |
| `escalate` | 升级给上级/管理员重新生成任务 |
| `fail` | 实例失败，进入死信流程 |

超时处理由**后台执行器的超时扫描器**驱动（见 docs/06），处理结果与正常操作一致地记录事件。

### 4.6 审批记录与审计

每次审批操作生成一条 `ApprovalRecord`：实例 id、节点 id、任务 id、操作人、动作、意见、时间、来自（人工/超时自动/管理员代操作）。前端审批中心与运营查询均基于该记录。

## 5. 自动动作（Action）

### 5.1 动作类型

| 类型 | 关键字 | 行为 |
| --- | --- | --- |
| HTTP 调用 | `http` | 按配置发起请求（method/url/headers/body），支持超时与响应解析 |
| 通知 | `notify` | 调用通知提供者（邮件/IM/短信），内容可模板化 |
| 延迟等待 | `wait` | 配合 `wait` 节点：按 `duration` 或 `until`（绝对时间）等待 |
| 内置函数 | `func` | 执行注册的内置函数（如 `calcAmount`、`genId`、`log`） |

### 5.2 输入输出映射

- `input`：动作执行前从上下文取值构造参数（JSONPath 模板）；
- `output`：动作结果（`$.result`）按映射写回上下文，供后续条件与动作使用；
- 结果包含 `ok`（bool）、`data`、`error` 三要素，`ok=false` 视为执行失败。

### 5.3 幂等与去重

- 每个动作实例带 `idempotencyKey`（支持 `${...}` 模板，如 `leave-${$.instance.id}-notify`）；
- 执行器在执行前按 `(instanceId, nodeId, idempotencyKey)` 查重：**已成功则直接跳过并复用结果**；
- 保证：重试、多副本并发、断点续跑均不会产生重复副作用（HTTP 侧配合请求头 `X-Idempotency-Key`）。

### 5.4 动作注册表与扩展

- `action.Registry` 提供注册/查找能力，内置 4 类动作；
- 业务方可注册自定义动作（实现 `Action` 接口：`Execute(ctx, params) (Result, error)`）；
- 未知动作类型在定义校验阶段即被拒绝。

## 6. 失败与恢复

### 6.1 错误分类

| 分类 | 判定 | 处理倾向 |
| --- | --- | --- |
| 可重试错误 | 网络超时、HTTP 5xx、临时性资源不可用 | 按 retry 策略重试 |
| 不可重试错误 | 参数非法、HTTP 4xx、动作类型不存在 | 不重试，直接失败 |
| 业务失败 | 动作返回 `ok=false` 且标记 `retryable=false` | 按 onFailure 处理 |

引擎根据错误类型与节点 `retry` / `onFailure` 决定路径。

### 6.2 重试策略

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `maxAttempts` | 3 | 最大尝试次数（含首次） |
| `interval` | `1s` | 首次重试间隔 |
| `backoff` | `exponential` | `fixed`（固定间隔）/ `exponential`（指数退避，间隔 ×2）/ `linear`（线性 +N） |
| `maxInterval` | `1m` | 退避上限 |
| `retryableErrors` | 见 6.1 | 仅该列表内错误触发重试 |

重试状态持久化在节点实例（`attempts`、`nextRetryAt`、`lastError`），重启后由执行器按 `nextRetryAt` 续跑。

### 6.3 节点超时

- `wait` 节点按自身 duration/until 推进，其余节点由 `timeout` 触发；
- 超时视为可重试错误（若未超过 maxAttempts）或进入 `onFailure` 策略；
- 超时判断由执行器定时扫描（`nextRetryAt` / `deadline` 字段）。

### 6.4 死信（Dead Letter）与人工干预

- 超过 maxAttempts / 不可重试错误且 `onFailure=fail` → 节点 FAILED → 实例进入 **DEAD**（若 `recovery.deadLetter=true`）或 **FAILED**；
- 死信实例不自动推进，管理员可通过 API `POST /instances/{id}/retry` **重新入队**（从失败节点重试）或 `POST /instances/{id}/restart`（从起始节点重跑）；
- 死信列表在 API 与前端"运维视图"可见，含失败原因、尝试次数、最后错误。

### 6.5 补偿（Compensation）

- 节点可声明 `compensation`（逆向动作或反向 HTTP 调用，同样走幂等键）；
- 触发场景：`onFailure=compensate`、实例被取消（cancel）时对已完成节点按**逆序**执行补偿；
- 补偿执行同样记录事件与审计；补偿本身失败会再次触发重试/死信。

### 6.6 断点续跑

- 每个节点的**输入、输出、状态、重试信息**均持久化；
- 执行器推进采用"乐观锁 + 版本号"（`instance.version`），每次推进校验版本，冲突则重读重算；
- 进程重启：调度器重新扫描 `PENDING/RUNNING/WAITING_RETRY` 实例，从各自断点继续，无需人工干预。

## 7. 状态机

### 7.1 实例状态机

| 状态 | 说明 | 可迁移到 |
| --- | --- | --- |
| `PENDING` | 已创建未开始 | RUNNING |
| `RUNNING` | 推进中（至少一个节点在执行/等待） | WAITING_APPROVAL、WAITING_ACTION、WAITING_RETRY、SUSPENDED、COMPLETED、FAILED、TERMINATED |
| `WAITING_APPROVAL` | 有审批任务待处理 | RUNNING（审批完成）、SUSPENDED、TERMINATED |
| `WAITING_ACTION` | 自动动作执行中/等待恢复 | RUNNING、WAITING_RETRY |
| `WAITING_RETRY` | 重试退避中 | RUNNING（到点重试）、DEAD |
| `SUSPENDED` | 人工暂停 | RUNNING（恢复） |
| `COMPLETED` | 正常完成 | 终态 |
| `FAILED` | 失败（无死信） | 终态（可 restart 重建实例） |
| `DEAD` | 死信，等待人工干预 | RUNNING（retry/restart 后） |
| `TERMINATED` | 被取消/驳回终止 | 终态 |

### 7.2 节点状态机

| 状态 | 说明 | 可迁移到 |
| --- | --- | --- |
| `READY` | 已激活待执行 | RUNNING |
| `RUNNING` | 执行中 | SUCCEEDED、FAILED、WAITING |
| `WAITING` | 等待（审批/重试退避/延迟） | RUNNING、FAILED |
| `SUCCEEDED` | 完成，输出已写回 | 终态 |
| `FAILED` | 失败（触发实例级处理） | 终态（retry/restart 会重建） |
| `SKIPPED` | 因条件/策略跳过 | 终态 |

### 7.3 关键状态迁移规则

1. `RUNNING → WAITING_APPROVAL`：审批节点激活生成任务时；
2. `WAITING_APPROVAL → RUNNING`：任务满足通过条件（或超时自动处理）时；
3. `RUNNING → WAITING_RETRY`：可重试错误且未达上限时；
4. `WAITING_RETRY → RUNNING`：到达 nextRetryAt 时；
5. `RUNNING → DEAD/FAILED`：不可重试错误或重试耗尽时；
6. `RUNNING → COMPLETED`：end 节点激活完成时；
7. `PENDING → TERMINATED`、`WAITING_* → SUSPENDED → RUNNING`：人工操作。

## 8. 事件与审计

- 每个状态迁移、节点完成、审批操作、重试、失败均生成 `ExecutionEvent`：`(instanceId, type, nodeId, actor, detail, occurredAt, seq)`；
- `seq` 全局单调递增，SSE 按 seq 推送给前端，实现实时事件流；
- 事件持久化（store），支持按实例/类型/时间范围查询，作为审计依据；
- 事件类型枚举：`INSTANCE_STARTED / NODE_ENTERED / NODE_SUCCEEDED / NODE_FAILED / APPROVAL_CREATED / APPROVAL_APPROVED / APPROVAL_REJECTED / APPROVAL_TRANSFERRED / RETRY_SCHEDULED / DEAD_LETTERED / INSTANCE_COMPLETED / INSTANCE_TERMINATED / INSTANCE_RESUMED / INSTANCE_SUSPENDED / ACTION_EXECUTED / COMPENSATION_EXECUTED / VALIDATION_FAILED ...`。

## 9. 典型业务场景

### 9.1 请假审批（含会签与驳回）

提交 → 主管单人审批 →（驳回→回到提交节点重提）→ 天数>3 走 HR 会签 → 通知结果 → 结束。见 2.5 示例定义。

### 9.2 发布上线（含条件分支与自动动作）

提交发布单 → 代码门禁（自动动作：调 CI 检查，失败重试 3 次）→ 测试环境部署（动作）→ 测试负责人审批 → 生产审批（会签：开发负责人+架构师）→ 生产部署（动作，幂等键=发布单号）→ 冒烟验证（条件：验证通过）→ 通知 → 结束；任一失败进入死信，由发布管理员人工干预。

### 9.3 订单风控（含并行与汇聚）

订单创建 → 并行触发：风控评分（动作）、黑名单检查（动作）、人工复核（审批）→ 汇聚 → 条件判断：`score < 60 and blacklisted == false` → 放行（动作）/ 拒绝（动作+通知）→ 结束。

## 10. 非功能特性

| 特性 | 设计要点 |
| --- | --- |
| 并发安全 | 实例推进持版本号乐观锁；多副本执行器用租约互斥 |
| 幂等 | 节点执行、动作副作用、审批操作全部幂等 |
| 可观测 | 事件全量落库、指标暴露（见 docs/08）、SSE 实时流 |
| 安全 | 审批操作人校验、API 鉴权占位（可插拔 AuthProvider）、审计留痕 |
| 性能 | 实例推进批量扫描（每轮最多 N 个）、上下文按需快照、索引覆盖查询 |
| 可配置 | 调度周期、worker 数、租约时长、扫描批次等均走 config（docs/03 config 模块） |
