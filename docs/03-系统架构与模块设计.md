# 03 · 系统架构与模块设计

## 1. 分层架构

严格分层、单向依赖，**禁止反向依赖与循环依赖**（由 `go vet` + 依赖检查工具在 CI 强制）：

```
┌──────────────────────────────────────────────────────────────┐
│ cmd/server           入口：解析配置、组装依赖、启动 HTTP/执行器  │
├──────────────────────────────────────────────────────────────┤
│ api (REST 处理器/DTO/路由)    executor (调度器/Worker)          │
│ validator (定义/运行校验)                                      │
├──────────────────────────────────────────────────────────────┤
│ engine (状态机/流转/节点编排)                                   │
│   ├── condition (条件评估)  ├── action (自动动作)              │
│   ├── approval (审批逻辑)   └── recovery (重试/死信/补偿)       │
├──────────────────────────────────────────────────────────────┤
│ store (持久化接口: 内存实现/SQL 实现)    migrate (Schema 迁移)  │
├──────────────────────────────────────────────────────────────┤
│ model (领域模型: 定义/实例/节点/事件, 零依赖)                   │
├──────────────────────────────────────────────────────────────┤
│ config (配置加载与校验)                                        │
└──────────────────────────────────────────────────────────────┘
```

依赖规则（自上而下）：

| 层 | 允许依赖 | 禁止依赖 |
| --- | --- | --- |
| model | 标准库 | 任何 internal 包 |
| config | 标准库 | internal 其他包 |
| store | model、config | engine、api、executor 等上层 |
| condition / action / approval | model、store（读上下文/审批数据） | engine、api |
| engine | model、store、condition、action、approval、recovery | api、executor、validator |
| recovery | model、store、action | engine（避免循环，由 engine 调用 recovery） |
| migrate | store、config | 上层 |
| api | model、store、engine、validator、config | executor（通过事件通道解耦，见下） |
| executor | model、store、engine、config | api |
| validator | model、condition、action | api、executor |

> 解耦要点：api 与 executor **都依赖 engine 与 store，彼此不依赖**；前端实时事件通过 store 中的事件表 + SSE 通道订阅（`api` 订阅 `store.SubscribeEvents`），执行器写入事件后由订阅通道广播。

## 2. 核心协作时序

### 2.1 创建定义并启动实例

```
客户端 → api.workflow_handler: POST /workflows
       → validator.ValidateDefinition(def)        # 图结构/表达式/动作参数校验
       → store.SaveWorkflowDefinition(def)
客户端 → api.workflow_handler: POST /workflows/{id}/instances
       → engine.StartInstance(def, bizKey, ctx)   # 校验上下文、创建实例与 start 节点
       → store.SaveInstance(inst)                 # 实例持久化，状态 PENDING
执行器 → scheduler 扫描到 PENDING 实例 → worker → engine.Advance(inst)
       → start 节点完成 → 沿边推进 → 下一节点激活……
```

### 2.2 审批节点

```
engine.Advance → approval.Manager.CreateTask(inst, node) → 实例置 WAITING_APPROVAL
客户端 → api.instance_handler: POST /instances/{id}/approvals/{taskId}/approve
       → approval.Manager.Approve(task, actor, opinion)
       → 模式判定：会签未满 → 记录并等待；已满 → 节点 SUCCEEDED
       → engine.Advance → 条件节点求值 → 下一节点……
```

### 2.3 失败恢复

```
worker 执行 action 节点失败(可重试)
→ recovery.RetryPolicy.Next(attempts, err) → 需要重试
→ 节点置 WAITING_RETRY(nextRetryAt) → 实例 WAITING_RETRY → 持久化
调度器扫描到 nextRetryAt 到期 → engine.Advance → 重新执行
尝试耗尽 → recovery 判定死信 → 实例 DEAD → 事件广播 → 前端"死信"可见
管理员 → POST /instances/{id}/retry → 实例回 RUNNING → 从失败节点重试
```

## 5. 配置设计（config 模块）

```yaml
server:
  addr: ":8080"
  readTimeout: 10s
store:
  driver: sqlite            # memory | sqlite | postgres
  dsn: "./data/gflow.db"
  autoMigrate: true
executor:
  schedulerInterval: 1s     # 调度扫描周期
  scanBatchSize: 100        # 每轮最多推进实例数
  workers: 8                # Worker 池大小
  leaseDuration: 30s        # 实例租约时长
  leaseRenewInterval: 5s
  timeoutScanInterval: 10s  # 审批/重试超时扫描周期
api:
  auth:
    provider: none          # none | header(占位，可插拔)
  cors: true
logging:
  level: info
```

配置加载顺序：默认值 ← 配置文件 ← 环境变量（`GFLOW_*`）← 命令行 flag；加载后统一校验，非法配置启动即失败（启动自检，见 docs/08）。

## 6. 依赖注入与组装

`cmd/server/main.go` 负责依赖组装（不使用重型 DI 框架，手写 wiring）：

```
config.Load → store.New(driver) → migrate.Run(store, dir) → model/event 通道初始化
→ condition.NewRegistry / action.NewRegistry（注册内置动作）
→ approval.NewManager(store) → recovery.New(...) → engine.New(store, cond, act, appr, rec)
→ validator.New(...) → executor.New(scheduler, workers) → api.NewRouter(handlers...)
→ 启动 executor（后台）→ 启动 HTTP → 监听信号做优雅停机
```

## 7. 关键设计决策记录（ADR 摘要）

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 定义格式 | JSON（版本化 + 校验） | 通用、易读、前端 JSON 编辑器零成本 |
| 存储 | 接口 + 内存/SQL 双实现 | 开发测试用内存，生产用 SQL；接口隔离便于换库 |
| 推进方式 | 调度器轮询 + 乐观锁 | 相比事件驱动更简单可靠，天然支持重启续跑 |
| 多副本 | 租约互斥 | 避免两个副本同时推进同一实例 |
| 前端 | 静态页面 + go:embed | 无构建链、单二进制分发，满足"简单前端" |
| 事件流 | SSE | 单向实时推送足够，实现简单；WebSocket 为后续增强 |
